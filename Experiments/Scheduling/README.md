## 1. 当前实现做了什么

核对范围：[ScheduleEngine.swift](../../Sources/StudyCore/ScheduleEngine.swift)、[SchedulePreferenceOptimizer.swift](../../Sources/StudyCore/SchedulePreferenceOptimizer.swift)、[ScheduleFeasibilitySearch.swift](../../Sources/StudyCore/ScheduleFeasibilitySearch.swift)、[SchedulePriorities.swift](../../Sources/StudyCore/SchedulePriorities.swift)、[SchedulePreferenceTests.swift](../../Tests/StudyCoreTests/SchedulePreferenceTests.swift)，以及 Android 的 [Planner.java](../../Android/src/local/studyplanner/Planner.java)、对应的三个 Schedule 文件和测试。

### 评分定义

评分是字典序：先比较最重要项，相同才比较下一项，不是权重加总。同级按 diversity、dailyWeight、coursePriority、balancedLoad 的默认次序。内部每个规则还含固定的子项次序。

| 项 | 当前实际定义 | 含义与边界 |
|---|---|---|
| 混排覆盖 | 每天 `C(min(3, 科目数), 2)`，整份课表求和，越大越好 | 0/1/2/3 科分别计 0/0/1/3；第 4 科没有额外分。不等于混排天数 |
| 较早混排 | 上述每日覆盖乘“剩余日数”，求和，越大越好 | 总覆盖相同时，更早集中混排胜出，甚至先于同科相邻次数 |
| 同科相邻 | 仅在至少两科的日期，计相邻同科课节数，越少越好 | 单科日的长串同科不罚；没有按连续分钟或最长串长度评分 |
| 每日加量 | 分科分日学习量与目标量的平方误差 | 目标按已排入总量 × 倍率 / 可学习日数，依日期依次分配，剩余耗尽后目标为 0；仅倍率 >1 的课程参与 |
| 课程优先级 | 每当高优先级课节排在低优先级课节后，累计双方分钟数乘优先级差 | 比较整份课表的先后，不只是当天第一节 |
| 总负担均衡 | 每日总学习分钟平方和，再比较分科每日分钟平方和 | 不按当天可用容量归一化；只在更高规则相同时生效 |
| 最后破同分 | 开始分钟（相对第一天零点）× 课节分钟，求和 | 前面的目标完全相同时才尽早排 |

**默认特殊例外**：只要最终规则顺序仍是默认顺序（包括全部设为同级），`tripleBoost` 会放在所有规则之前。它是三倍课程的加量误差。因此默认界面虽显示混排优先，实际允许三倍集中先赢。单科日不计重复也是既有例外。本轮完整保留这些定义，没有改评分。

每日加量不增加总课时，也不改变截止日。例如 240 分钟、4 个可学习日、2 倍时，偏好目标为 `[120,120,0,0]`；放不下可延后。初始构造阶段还偏好前 `ceil(可学习日数 / 倍率)` 天。重排按新的剩余量、窗口和可学习日重算目标，不是永久固定的逐日额外债务。若基线未排完整，优化器的目标只基于已排入量；所以实验禁止把该局部评分直接与完整计划比较。

### 搜索能力与可能漏解的位置

1. 先按截止日期、需求强度等排程；尝试碎片搬移修复（最多 200 次）。初始混排从全部未完成工作重建，并按截止日群组检查是否丢失已排入量，必要时回退。
2. 未排完整时，联合交织课程队列和浮动事项。最多 6 科、600 块、1500 学习窗口、366 浮动事项；单日最多一个浮动事项，连续占用至少 15 分钟；beam 宽 128，扩展 250000 次。失败返回 nil，不是无解证明。
3. 已有课表再做整份评分：压紧、日间重新分配、当日交替、单节移动、两节交换。局部预算为 `max(32,min(12000,6000000/(课节数+天数×科目数)))` 次打包尝试。
4. 较密的长短混合课节可触发队列重建：至少 2 科、20 节、7 天、3 种时长且存在混排不足。范围至多 6 科 / 600 节 / 366 天 / 1500 窗口；两个方向各扩展 60000 次，beam 宽 4–32。
5. 浮动事项初始占位还有独立的 20000 次尝试上限，以尽量减少与可学习时段重叠。后续偏好优化固定这组浮动位置，不继续联合移动它们。

当前并非只会挪一节；它已经能重建整份课表。但小于上述重建门槛的课表仍可能卡在单节 / 两节邻域。beam 丢弃路径、启发式排序、只保留有限队列前缀和预算截止，都可能丢掉更好的安排。队列 beam 的 pace / 重复等代理排序也不是最终完整评分的精确下界，不能据此证明最优。

Android 的上述最终评分、倍率目标、三倍例外、局部预算、重建门槛与默认救援预算与 Swift 对应。Java 还有线程中断检查。实际跑过 Android 全套测试及 Swift 的 24 种优先级顺序、2 组密集课表跨端对照；这支持这些案例一致，不代表任意输入都已证明一致。README 中“Android 沿用原排程”等旧边界文字不足以代表当前源码。

## 2. 对照模型与公平边界

基线直接编译当前 StudyCore 的 Release 优化代码；仅在临时副本插入窗口捕获，并开放内部 Search 的可见性供评分复核，原算法函数体不改。源码锚点不匹配就报错。正式 Package.swift 不增加任何目标或依赖。

| 硬约束 | 建模 / 核对方法 |
|---|---|
| 开始日、截止日 | 沿用当地整日含截止日的语义；每节的整数分钟开始域裁到课程日期和实际开课下界 |
| 整节、顺序、总量 | 从生产 `lessonWorkItems` / `remainingMinutes` 取得逐节余量；每节一个固定时长 interval，所有剩余课节必须存在；同科前后节加先后约束 |
| 学习窗口、固定事项 | 使用生产日期与事项发生规则生成区间；学习 interval 必须完整处于扣除固定占用后的一个连续窗口 |
| 浮动事项 | 每次发生一个固定时长 interval，开始域在原窗口内；与其他浮动和学习不重叠，可在学习窗口外占用 |
| 休息 | 学习课节的全局时间顺序 circuit，邻节至少间隔 15 分钟，跨窗口、跨日保留；浮动事项可占用休息；固定事项不凭空要求额外休息；末节不额外占窗口内尾休息 |
| 部分完成、历史、确认 | 复用生产进度核算，保留历史及确认占用的缓冲区；同日确认时间和实际开课下界取最大值；不改写流水或历史 |
| 锁定 | 模型可用 `locked` 固定指定任务开始位置，单测验证不会被优化移走；正式项目尚无任意任务拖拽锁定功能 |

本适配器只生成不含个人数据的按节合成课程，不是通用 PlannerState 导入器。普通课程块化、网站 / 合并课程复杂进度、十年极端范围、夏令时等尚未端到端覆盖；进度接口的已有测试不等于新模型全覆盖。保存的当日拖动顺序 `dailyTaskOrders` 是正式算法结束后的可行时恢复步骤，不是任意任务锁。实验遇到它会明确拒绝导出，不会静默丢弃。接入前必须补齐该适配。不会把这些范围外情形声称为“已验证”。

偏好目标完全沿用当前函数。每日加量目标冻结为当前课表的实际评分窗口对应的目标，两个求解方法共用；移动浮动事项不会趁机改变目标定义。CP 模型采用有理数整倍缩放，候选解各目标同时与独立 Python 评分核对，再与 Swift 原评分逐项核对（本轮 83 次完整计划）。支持范围内的分数间隔大于生产比较容差 1e-6。极端小数的倍率若导致缩放过大，模型会拒绝，而不会近似冒充精确。

分层求解每次只优化一个分量；得到 OPTIMAL 才添加“该分量等于已证最优值”，再处理下一项。FEASIBLE 或 UNKNOWN 即停，不继续低层。所有层均证明才标整份方案 OPTIMAL。LNS 即使子问题证最优，也只代表该固定邻域；整份不称最优。

LNS 从现有完整课表出发，按相邻两天或两门课程释放一批任务，其他任务保持开始时间；浮动事项仍可在原窗口移动。每批使用 CP-SAT 修复，只接受按同一完整向量严格改善的完整方案。不是拿“大数权重”混合目标。全局 CP 的原始候选如果比基线差，会标为拒绝并保留基线。本轮没有这种被拒退步。

每例 CP 与 LNS 各有 3 秒总预算，大例各 8 秒；包括各自建模，单 worker、固定 seed=20261023。基线沿用现有操作预算，并记录 `-O -whole-module-optimization` 下的原生运行时间；它所有例均在对应上限内结束。没有声称三种方法消耗相同 CPU 时间，也没有用“重复运行现有算法直到 3 秒”虚增工作。比较的是同输入、同规则、明确的各自预算与实际成本。API 收尾和不能中断的模型构造可能略超时，实际耗时照录；若建模已超预算则不启动求解。

## 3. 实际证据

案例参数优先复用现有均衡、倍率优先、满日交换、不同截止日、浮动事项与 88 节密集回归结构；课程统一使用实验稳定 ID，故不是原测试序列化字节的原样重放。另保留固定种子的 8 个普通、8 个接近满载小例，不筛掉不改善或无解的例子；再加部分完成、历史、晚开课、分数倍率和优先级优先。机器输入、所有源码 SHA-256、运行环境、各层状态与界限可在原始 JSON 查看。

三次完整运行中，小例的 CP 状态和全部最优向量一致；大例的 CP 都是 UNKNOWN，LNS 的前八项评分一致，最后的时间破同分项有变化（86618175 与 86622800）。这说明即使固定种子与单 worker，墙钟预算下最后优化到哪一步仍受机器负载影响；不承诺限时大例逐字一致。结果表取稳定事项 ID 后的最后一次完整测量。

- **实际混排改善**：`seeded-tight-6`，615 分钟、10 节、4 天、每天 08:00–11:15。当前各日为 `[165,165,165,120]` 分钟，混排 3 天、同科相邻 2 次；CP 后为 `[165,165,120,165]`，混排 4 天、相邻 0 次。每科均完整按期，全部评分层证明最优。完整向量从 `[0,-5,-13,0,0,0,96075,51975,1558350]` 变为 `[0,-6,-12,0,0,0,96075,46575,1624050]`。较早混排子项和最后时间项变差，仍因更高的总覆盖改善而胜出，符合既有规则。
- **需要多节联合调整**：上例穷尽 175 个单节搬移 / 两节交换并重新打包，没有一个改善。新方案联合改变多节课的日期与顺序。`seeded-tight-1` 和 `seeded-tight-3` 也有同类局部停滞证据。LNS 能改善前两者中的 tight-1、tight-3，却未改善 tight-6，说明邻域设计仍重要。
- **评分胜出但直觉可变差**：`default-triple-exception` 的三倍误差 7200→0，全部按期且每天总负担不变，但混排日 3→2、同科相邻 0→2。CP 只是更严格实现了现有三倍例外，不能把它宣传成混排改善。`seeded-tight-3` 也是总覆盖增加但混排日 4→3、每日负担更不均；当前覆盖定义允许这种结果。
- **大例只有有限收益**：88 节共 6780 分钟，基线已全部按期，耗时约 0.1 秒。CP 8 秒内 UNKNOWN，没有证明不可行；LNS 约 8.03 秒，把混排日的相邻同科 4→3、优先级逆序 3879725→3709525，同时每日总量平方和 2912700→2930500、分科平方和 1168250→1235650 变差。这是按优先级允许的交换，不是均衡全面改善，也没有全局最优证明。
- **原方案已经很好**：27 个可证明小例中 23 个与现有评分完全相同。基线通常约 0.3–3 毫秒，CP 通常约数毫秒至数百毫秒；新工具增加了成本。当前未排完整的 4 例，CP 均证明无解，本轮没有“当前漏排、新工具补全”的案例，不能声称已改善可行解找到率。

结果表提供实际起止时间。对 tight-6，简写为科0=A、科1=B、科2=C，每个数字是一节的分钟数（节间休息未计入数字）：

|---|---|---|
| 第1天 | B90 → A75 | B90 → A75 |
| 第2天 | B90 → A75 | C30 → A75 → C60 |
| 第3天 | B75 → A60 → C30 | B90 → C30 |

## 4. 评分还是搜索，怎样接入

**搜索存在已证缺口**：保持评分不变，就有多个当前单节 / 两节邻域无法改善但全局可改善的小例。可先改进跨课节批量修复，收益可归因于搜索。无需为此先修改混排评分。

**评分定义也需要产品判断**：覆盖封顶三科、总覆盖优先于混排天数、单科日不计相邻、三倍例外优先于默认混排，都会让数学最优方案与“每天多科、不要集中”的直觉不同。若要改变，应另立评分实验，保持求解方法不变。本轮没有擅自替换这些定义，也没有把它们直接判为代码错误。

建议下一步先做可取消的后台候选优化：沿用现有快速课表，选压力大的两天 / 一段课节队列 / 特定截止日前的批次做 LNS，严格保留每科按期量与更高评分，接受前独立验证。过时输入取消结果，超时保留当前方案。先在独立预览或试验开关下收集可复核案例，再决定正式默认启用。不能让一次 8 秒 UNKNOWN 阻塞“生成课表”。

| 平台 | 实际接入成本与建议 |
|---|---|
| Mac | 试验阶段离线 Python 子进程成本较低，但正式 app 不能依赖本机恰好有 Python。可选捆绑隔离 helper 或 C++ 动态库加 Swift/C 桥；要处理库依赖、签名、包体、取消、内存、崩溃隔离、分钟与日期序列化。官方没有 Swift 绑定。本轮只验证 Python wheel 可运行，未构建该桥。先接 LNS 辅助，不替换快速路径 |
| Android | 现有工程是 javac/d8 脚本；桌面 Java API 不等于 Android 直接可用。需验证 NDK 交叉构建、JNI、arm64-v8a 等 ABI、原生依赖、包体、旧手机内存与耗电、生命周期取消。官方 Android 讨论仍指向 NDK/CMake 的构建尝试，不能据此承诺现成 APK 集成。可先沿用 Java 启发式，移植不依赖原生库的批量邻域思路，或同步 Mac 已验证候选；手机独立排程能力不能因此减少 |
| 双端一致性 | 先建立共享的规范化输入、评分向量、状态语义与合成金标准；相同模型的可行与最优值应一致，限时启发式的具体课表不要求逐字一致。补齐普通块、保存的拖动顺序、复杂完成进度后再谈正式集成 |

## 6. 官方资料与研究核查

- [CP-SAT 官方状态与整数建模说明](https://developers.google.com/optimization/cp/cp_solver)：核实 OPTIMAL、FEASIBLE、INFEASIBLE、UNKNOWN 的区别。状态只对当前模型成立，模型正确性仍需独立校验。
- [OR-Tools v9.14 官方排程建模文档](https://github.com/google/or-tools/blob/v9.14/ortools/sat/docs/scheduling.md)：核实 interval、NoOverlap、先后约束及序列建模。本实验用固定时长与时间域，不把课时压缩来提高完成量。
- [The CP-SAT-LP Solver，Perron / Didier / Gay，CP 2023](https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.CP.2023.3)：原作者对整数约束、SAT / 线性松弛及多种搜索策略的介绍。不能据竞赛或通用性能推断本项目会获益。
